# 纯直接 AI 排版改造方案

## 当前实现状态（2026-10-20）

本文件后文保留原始改造方案；实际接口和约束以 [format-profile.md](format-profile.md)、[direct-format-api.md](direct-format-api.md) 和当前代码为准。

已实现：要求材料提取、样例有效值快照、全部页面节、证据型 Profile 1.0、显式问题决策与规则/节映射、目标段落覆盖检查，以及同一核心的计划/应用/复检。视觉验收已迁移到直接 verify 入口，绑定输出、渲染清单和全部页面哈希。配置页面、会话服务、浏览器回归及 Node 开发依赖已移除，Skill 和当前使用文档统一为直接 AI 流程。

仍需明确处理的边界：扫描件 OCR、复杂浮动对象、任意表格几何、特殊节布局、复杂域和逐节页码制式不能靠通用数值规则完整还原。档案会保留证据及待处理项；AI 可编译已支持的明确操作，不能把忽略项称为迁移完成。视觉通过仍需实际渲染和全页检查。

## 目标与边界

本方案把 Word Format Master 改为**只通过当前 AI 会话和本地命令行完成格式工作**。用户用自然语言说明任务，并提供以下一种或两种材料：

1. 学校、期刊或机构的格式要求文档；
2. 一份已经排好版、用作格式样例的论文。

AI 负责理解任务、选择格式依据、定位目标论文中的语义角色，并决定何时需要澄清。项目代码负责从 DOCX 中提取可核验的格式证据、验证格式请求、以确定性方式写入格式、保护原稿及复核结果。最终输出为新的 DOCX 和一份可读的检查报告。

本项目可以把**声明支持的格式属性**准确读取、转换、写入并回读；不能对任意 Word 文件承诺“读取并复制所有可能的格式”。Word 包含浮动对象、表单控件、修订、嵌入对象、自定义 XML、复杂字段和厂商扩展等特性，某些项目既不能安全迁移，也无法仅靠数值规范还原。对这类项目必须报告覆盖范围或不支持项，不能静默忽略后仍声称完全一致。

## 当前基础与缺口

项目已经有适合继续发展的确定性核心：`format_cli.py` 提供 `inspect / audit / plan / apply / verify`；`word_format/registry.py` 登记可执行操作及参数验证、读回和验收；`analyze_docx.py` 提取 DOCX 包、样式继承、页面节、编号、页眉页脚、字段和部分论文模块；`parse_requirements.py` 可从纯文本识别一部分常见要求；`render_docx.py` 可用 Word 或 LibreOffice 渲染输出。

当前“直接告诉 AI”并非空白，但尚未构成用户说一句话、给一个样例就能稳妥完成整篇论文的闭环：

- AI 需要自行组合多个命令和 JSON；没有统一的“读取要求/样例、生成格式档案、匹配目标、执行、复核”任务入口。
- 文字要求解析器只接收纯文本，不能直接从 DOCX/PDF 要求文件中保留段落、表格、标题和页码等证据；解析结果也只能覆盖已编码的语言模式。
- DOCX 提取虽读取大量 OOXML 信息，`inferred_spec` 仍以常见正文、标题、参考文献、题注和第一个页面节等为中心，不是任意论文的逐属性完整快照。不同节、不同页型、局部直排格式和复杂对象必须扩大覆盖并明确报告。
- 参考论文中的格式值不能直接套到任意目标段落。还需要把样例的“章节标题/正文/摘要/参考文献/题注”等角色映射到目标文档，并发现目标中缺失、重复或含义不明的角色。
- 网页路径不只包含 UI 文件；本地 HTTP 服务、会话、提交后 handoff、分析轮询、下载运行库、文档和回归测试也依赖它。只删网页静态文件会留下不可运行的入口和测试。

## 目标工作流

```text
用户自然语言 + 要求文件/排版样例 + 目标论文
                 ↓
AI 判定任务类型、权威来源和修改范围
                 ↓
本地提取工具 → 带来源/置信度/覆盖率的 Format Profile
                 ↓
AI 处理冲突与未决项；必要时向用户澄清
                 ↓
inspect 目标文档 → 角色映射 → 生成可审阅计划
                 ↓
plan 校验 → apply 写入到新文件 → verify 独立回读
                 ↓
Word/LibreOffice 渲染 → 逐页视觉检查 → 输出 DOCX 与报告
```

不启动浏览器或本地 HTTP 服务，也不生成网页 handoff。格式操作始终走现有 registry、planner、writer 和 verifier；AI 不生成或执行临时 Python 写文档代码。

## 两种格式依据的处理契约

### 1. 格式要求文档

新增“要求材料提取”入口。第一版支持 UTF-8 文本/Markdown、DOCX/DOTX 和可提取文字的 PDF；旧版 DOC 先转成 DOCX，扫描版 PDF 需要 OCR 后再处理。DOCX 要遍历正文、表格、页眉页脚和文本框中可读取的文字，而不是只读顶层段落。PDF 保存页码和区块位置作为证据；PDF 的字体外观只能用于辅助判断，不能把 PDF 内容自动视为 Word 样式定义。

提取器输出原文片段及位置索引，再由现有规则解析器与 AI 语义解释共同生成候选字段。每个字段至少记录：字段路径、值、来源文件哈希、页码/段落/表格单元格等证据锚点、置信度、是否由用户锁定。未匹配内容进入 `unresolved`，冲突字段保留全部证据及权威级别。禁止用通用预设填补要求材料未写出的字段；用户明确选择“按整篇通用预设”时才可应用预设。

### 2. 已排版论文样例

扩展 DOCX 分析为可复用的模板档案，而不是只从样例提取几项数值。至少按以下范围扫描并区分“样式定义、继承后的有效值、段落/字符直接格式、文档默认值、主题值”：

- 全部页面节：纸张、方向、页边距、装订线、栏、页眉页脚距离、节起始类型和页码起始；
- 全部段落/字符样式：样式 ID、名称、类型、继承链、有效中西文字体、字号、颜色、粗斜体、段距、行距、缩进、分页属性、编号和大纲级别；
- 论文角色：封面字段、声明、摘要、中英文关键词、目录、符号表、章节标题各级、正文、参考文献、致谢、附录；保留顺序及样例中的段落锚点；
- 表格和题注：表格样式、边框、对齐、单元格边距、标题行重复、题注位置与样式；
- 页眉页脚：每节的默认/首页/奇偶页部件、是否链接前节、文字、样式、域代码和页码；
- 目录、交叉引用、页码和题注等字段；编号定义及其与标题/列表的绑定；
- 文档包中检测到的图片、浮动图形、文本框、公式、批注、修订、内容控件、嵌入对象和外部关系等特殊结构。

样式对齐必须以**有效格式**为依据，不能只复制样式名称。直接格式既可能是偶然例外，也可能表达加粗术语、公式字符或封面特例；提取时要保留其位置和分布，角色映射/应用前由证据决定迁移规则。不得将样例中的正文、姓名、题目、引用内容或页眉中的论文专属文字复制到目标论文。

目标论文应用样例时，先由程序建立文档对象目录，再由 AI 根据标题层级、样式、编号、上下文及正文/表格位置建立源角色到目标角色映射。映射置信度低、角色重复或目标缺少必要模块时，先请求澄清或把对应字段列为未应用；不得把正文误判为标题，也不得静默新建/删除论文模块。

### 3. 统一的 Format Profile

新增版本化的 `Format Profile` 数据契约，作为要求材料、排版样例、预设和最终修改计划之间的共同格式表示。建议字段如下：

```json
{
  "schema_version": "1.0",
  "source": {"kind": "sample-docx", "path": "...", "sha256": "..."},
  "authority": "user-template",
  "coverage": {"detected": [], "represented": [], "unresolved": [], "unsupported": []},
  "rules": {"page": {}, "roles": {}, "sections": [], "numbering": {}, "fields": {}},
  "module_contract": {"strict_order": true, "ordered_modules": []},
  "evidence": [{"field": "roles.body.line_spacing", "value": {}, "anchor": "...", "confidence": 1.0}],
  "conflicts": [],
  "unresolved": [],
  "notes": []
}
```

该示例是契约草案，不是当前已经支持的 JSON 输入。Profile 对每个字段区分“未发现、明确为空、无法判断”三种状态，保留来源优先级和用户锁定值；不得把缺失值等同于 `false` 或 0。把 profile 转为直接操作时，所有写入仍须经过 `capabilities` 中登记的 action 和参数验证。暂不支持安全迁移的包级结构会进入 `unsupported`，并在报告中指出对结果的影响。

权威优先级继续采用现有顺序：用户锁定字段 > 用户提供的院校/出版方模板 > 明确书面要求 > 用户指定的标准 > 用户选择的预设 > 目标论文原格式。不同来源同级冲突时暂停该字段，不靠 AI 猜测。对局部修改，目标文档对未请求属性仍是权威；对整篇归一化，用户选定的 profile 才可覆盖所声明的字段。

## CLI 与 AI 使用方式

保留现有命令，并加一个围绕 profile 的稳定直接入口。最终命令名可在实现时按兼容性确定，建议形态：

```powershell
python scripts/format_cli.py profile requirements "学校格式要求.docx" --output "论文规范.json"
python scripts/format_cli.py profile template "排版样例.docx" --output "论文规范.json"
python scripts/format_cli.py inspect "待修改论文.docx" --output "论文检查.json"
python scripts/format_cli.py plan "待修改论文.docx" "排版后.docx" --profile "论文规范.json" --request-text "整篇按规范排版" --output "修改计划.json"
python scripts/format_cli.py apply --plan "修改计划.json" --report "验收报告.json"
python scripts/format_cli.py verify --plan "修改计划.json" --report "验收报告.json"
```

当前 CLI 已实现上述 profile 命令；需要映射或决策时再传入 `--mapping` 和 `--resolutions`。规划命令应将 Profile 展开为 registry 操作，报告目标对象映射、将修改的字段、冲突、未决项和不支持项。存在高影响未决项时返回 `needs_clarification` 且不写输出。单一、明确的格式指令可继续直接使用现有 `inspect → plan → apply → verify` 方式；AI 不应为了局部调整套用整篇 profile。

更新 `SKILL.md` 和 `agents/openai.yaml`，让所有用户请求都按一种直接工作流处理：识别用户给的是文字要求、格式样例还是局部修改；读取源文件并先检查能力；输出格式依据摘要/低置信度问题；请求无歧义时自动计划和应用到新文件；运行结构验收；按渲染能力逐页检查并如实报告。Skill 要提供中英文自然语言示例、批量论文和局部段落场景，以及直接读取要求文档/样例的操作方法。它要优先调用 Profile 命令，而不是让用户手工编写 JSON。

## 分阶段实施

### 阶段一：固定直接入口契约

先整理 `direct-format-api.md`、`format_cli.py` 和 `SKILL.md`，定义用户需求到 inspect、计划、应用、验证的完整交互。保留现有执行器和操作注册表，避免在移除网页时重写已成熟的格式核心。建立一份清楚的支持能力清单和结果报告字段：`applied / verified / unresolved / unsupported / visual_status`。

**验收：**一项明确的局部格式请求和一项整篇预设格式请求都可通过直接 AI 工作流完成，原稿不变，计划和输出路径绑定，失败时不发布半成品。

### 阶段二：打通要求文档读取

增加要求文件抽取器，复用 `parse_requirements.py` 的词法规则，但把它从“整段纯文本正则解析”升级为有结构、有证据锚点的解析。针对 DOCX 遍历正文、表格及页眉页脚；针对 PDF 按页提取文字与坐标。先支持可读取文本，不把 OCR 能力误称为已覆盖。将版式要求按字段拆分、绑定来源和置信度，保留原文锚点与未解析段落。

**验收：**测试夹具覆盖中文/英文、表格内要求、多个同名章节、显式否定、单位转换、同字段冲突、缺省字段和 PDF 页码锚点；没有证据的值不得写入 Profile。

### 阶段三：形成完整样例论文档案

扩展 `analyze_docx.py` 及其解析模块，把每节、每种页型、全部相关样式及直接格式统计纳入 Profile。为字段提供“有效值由何处继承”的来源链。分析报告同时列出 OOXML 包清单、可识别内容覆盖、拒绝分析/写回的特性和人工检查要求。把当前单一 `inferred_spec` 的抽取改为可重复校验的 Profile，不以首节页面值代表整个文档。

**验收：**合成和脱敏真实模板涵盖多个节、继承样式、主题字体、首页/奇偶页、字段、三级编号、图表、表格、文本框和修订。分析 JSON 对可支持属性与 Word/OOXML 读取结果逐项比对；不支持项在报告中可见。

### 阶段四：实现样例到目标的角色映射

扩展目标文档对象索引和论文模块识别。AI 可在受约束的 inspect 证据上提出语义映射，但最终计划保存具体段落/样式 ID、输入哈希和映射证据。对无法确定的标题级别、封面字段、摘要语言、图表归属、表格题注和跨节格式，不默默选一个。先支持常见段落样式、页面节、页眉页脚、标题编号、目录、题注、表格和参考文献；特殊 OOXML 结构按兼容矩阵逐步加入。

**验收：**样例与目标中的内容不同但模块角色一致时格式可迁移且目标正文不被覆盖；目标中缺少/多出模块、角色重复或章节编号歧义时得到稳定的澄清状态，而不是错误应用。

### 阶段五：统一 apply、回读与视觉验收

Profile 计划只能展开为 registry 已登记操作。扩展计划报告，逐字段记录来源、源/目标角色、期望值、写入 handler、实际回读值和状态。运行现有包级保全、文档结构和哈希校验；对不支持的字段拒绝声称已完成。继续使用 `render_docx.py` 检查全页布局，说明 Word 与 LibreOffice 分页可能不同；视觉模型无法读取图片时报告 `skipped`，不能把 `pending` 或结构通过说成视觉通过。

**验收：**注入错误写入器时独立读回能使验证失败；源文件、无关对象及未请求属性不变；结构完整性通过但存在渲染异常时最终状态不通过。

### 阶段六：彻底删除 Dashboard 并清理工程入口

在直接链路有回归保护后，按本方案文件清单删除网页、服务器、session、handoff、浏览器测试和 npm 依赖。将 `validate_project.py` 和 `smoke_test.py` 改为验证纯直接路径，确保全新克隆无需 Node/Playwright/NPM 即可开发、验证和使用。同步调整 CI、README、Skill 元数据、安全说明和版本记录。

**验收：**仓库中不存在可启动的 Dashboard、浏览器配置 URL、Dashboard API、提交 handoff 或 UI 模拟路径；文档搜索不再把网页描述为可用入口；核心测试和 Windows CI 通过。

## 测试与交付门槛

改造前基线：当前 Python 单元测试 **74 项通过**（本次本地完整运行，约 242 秒）。改造过程中保留这一组核心测试的等价覆盖，并增加：

- 要求材料抽取、证据锚点、冲突与未解析字段测试；
- 多节、多页型、继承链和直接格式的 Profile 快照测试；
- 角色匹配和低置信度不执行测试；
- Profile → 操作计划 → 新 DOCX → 独立 verify 的端到端测试；
- 不支持 OOXML 特性明确报告且原包未损坏的测试；
- Git 全库网页入口/依赖残留扫描和干净环境 CLI 安装测试；
- 使用脱敏的真实学校模板逐页渲染人工对照，覆盖 Word；LibreOffice 验收单独报告。

每个支持字段至少要有：输入/证据测试、规范校验、唯一写入方、独立读回器、输出保全检查和视觉样例（适用时）。不要求每个数值属性都重复造端到端测试，但必须覆盖模板提取与应用迁移的组合路径。

## 主要风险与取舍

- **“所有格式”范围无限。** 通过 Profile `coverage` 明确可识别、可表示、可应用、已验证四种覆盖程度，并对未知结构暴露降级；优先扩展最常见的论文版式和模板功能。
- **样例的内容和格式混在一起。** 只迁移版式字段及语义角色；页面中的姓名、题目、文字和引用不能被误当成规范。学校模板 DOCX 若要保留其专属封面和复杂部件，后续应提供“模板作为新文档母版”的专用迁移模式，与普通样例论文提取格式档案区分。
- **页面视觉不等于 OOXML 数值一致。** 结构读回和渲染是两个独立门槛；Word 为最终分页参照，浏览器预览或 LibreOffice 不能替代 Word 的最终确认。
- **整体覆盖和局部保留冲突。** 整篇归一化必须由用户清楚授权；局部修改严格只写指定字段。缺少来源值时不自动补零、不套预设。
- **删除网页时可能误删共享职责。** 先迁移 `apply_spec.py` 中仍被测试/核心调用的兼容函数，再删 handoff 文件；保留现有核心函数和已有数据的迁移路径。

## 建议的实现顺序

建议先完成阶段一，再推进要求文档提取、样例档案和角色映射；待直接链路覆盖回归并稳定后，最后执行阶段六的完整删除。为避免一次性大改造成格式质量倒退，核心格式引擎不要与网页删除同时整体重写；每一阶段单独通过测试后再合并。完成后用户只需给出“目标论文 + 要求文档/样例论文 + 输出路径”，AI 便能走同一条有证据、可复核的本地直接流程。
